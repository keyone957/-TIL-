### OS 입장에서 스택이 어디에 있는지 어떻게 판단하나요?

<aside>

> OS가 스택의 위치를 실행 중에 탐색하는 것은 아님. 프로세스나 스레드를 생성할 때 OS가 가상 메모리 공간에 스택 영역을 미리 할당하며, 현재 스택의 위치는 CPU의 SP(스택 포인터) 레지스터가 가리킴

각 스레드는 독립적인 스택과 SP를 가지며 OS는 문맥 교환 시 TCB에 저장된 SP값을 저장하고 복원하여 각 스레드의 실행을 이어간다.

</aside>



### 멀티 스레딩

<aside>

하나의 **`프로세스`** 안에서 여러 **`스레드`**가 **자원을 공유**하며, **`프로세서`**의 코어들이 여러 스레드들을 활용해 **`동시에 작업을 수행`**하는 방식

</aside>

만일 CPU가 멀티 코어라면 진짜 병렬적으로 스레드가 각각 코어에 할당이 되어서 실행이됨.
이런 종류의 시스템을 멀티스레딩

* **하나의 프로세스가 동시에 여러 작업을 실행하는데 목적**

스레드의 등장으로 인해 확장된 멀티 태스킹 개념
→ 여러 프로세스와 여러 스레드가 아주 짧게 쪼개진 CPU TIME을 나눠 갖는 것

<aside>

### 멀티스레딩의 문제점 및 해결 방법

### **`1. Race Condition`**

> 여러 스레드가 같은 공유 데이터에 동시에 접근하여 실행 순서에 따라 결과가 달라지는 문제

ex) 두 스레드가 동시에 하나의 변수에 접근하여 조작하면 원하는 결과가 나오지 않을 수 있음
공유 변수 count=0;
쓰레드 a : count ++; / 쓰레드 b : count++;

#### **해결 방법**

동기화 기법 (뮤텍스, 세마포어, 모니터)

### `2. Critical Section 문제`

> 여러 스레드가 동시에 접근하면 안되는 공유 코드 영역 ⇒ 이 구간에 여러 스레드가 동시에 들어가면 데이터가 잘못될 수 있다.

#### **해결 방법**

임계 영역을 설정하고 상호 배제를 보장한다.
한 스레드가 입계 영역에 진입 → 다른 스레드 대기 → 작업 종료 후 Lock을 해제

### **`3. 데드락`**

> 두 개 이상의 스레드가 서로 상대방이 가진 자원을 기다리며 영원히 멈추는 문제

### **`4. 기아 현상`**

> 특정 스레드가 계속 자원을 얻지 못하고 실행되지 못하는 문제

#### 해결 방법

* 공정한 스케쥴링 사용
* 대기 시간이 긴 스레드의 우선순위를 높이는 Aging 적용  
  
  </aside>

<aside>

### 정리

멀티스레딩은 같은 프로세스의 메모리를 공유하기 때문에 Race Condition이나 데드락 같은 동기화 문제가 발생할 수 있습니다. 이를 해결하기 위해서는 뮤텍스, 세마포어, 등을 사용할 수 있딩으며 가장 좋은 방법은 공유 상태와 임계 영역을 최소화 하는것임

</aside>



### 멀티프로세싱

<aside>

하나의 **`프로그램`**을 여러개의 독립적인 **`프로세스`**로 나누어 구성하고 이를 다수의 **`프로세서(cpu)`**가(싱글코어 x 멀티 코어 이상) 동시에 병렬적으로 처리하는 기술

</aside>

→ 두 개 이상의 프로세서나 코어를 활용함

<aside>

### 멀티프로세싱의 문제점 및 해결 방법

### `1. 컨텍스트 스위칭 비용`

> 프로세스를 전환할 때는 스레드 전환보다 더 많은 CPU상태와 메모리 관련 정보를 교체해야 함.

#### 해결 방법

* 프로세스 수를 CPU 코어 수에 맞게 제한
* 작업을 너무 작은 단위로 분리하지 않기

### `2. 메모리 사용량 증가`

> 각 프로세스는 별도의 주소 공간을 가지므로 같은 데이터를 사용하더라도 각각 메모리를 차지할 수 있음

#### 해결 방법

* 프로세스 수 제한
* 공유 메모리 사용

### `3. 프로세스 간 데이터 공유가 어려움`

> 프로세스는 메모리를 공유하지 않기 때문에 직접 변수에 접근할 수 없음

#### 해결 방법

⇒ IPC사용

</aside>
